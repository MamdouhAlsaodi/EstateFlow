# EF-120 Implementation Plan — Browser Cookie Sessions and CSRF

## Status

PASS

## Goal and authority

Produce an implementation-ready plan for EF-120, constrained by accepted [ADR-007](../../architecture/auth-session-adr.md). This is a source-grounded plan only; no product source, dependency manifest, schema, service, Git, or infrastructure was changed.

Source facts used: the API is NestJS 11.1.28 on Express, Node is pinned to 24.14.1, Prisma is 6.19.0, the schema currently has only the PostgreSQL datasource and the database baseline migration, tests use `node:test`, and OpenAPI/client generation currently supports only health endpoints. Test PostgreSQL is an isolated PostGIS container on loopback port 55433; its existing guard requires `ALLOW_DESTRUCTIVE_TESTS=1` and the `estateflow_test` user/database.

## Design constraints carried forward

- Browser-only, same-origin cookies; no bearer, mobile, partner, or external API credential flow.
- The only browser cookies are `__Host-estateflow_access` (15 minutes), `__Host-estateflow_session` (7-day absolute / 24-hour idle), and readable `estateflow_csrf`; all are `Secure; SameSite=Lax; Path=/` with no `Domain`; the first two are `HttpOnly`.
- Access and refresh values contain at least 256 bits of CSPRNG secret material. The database never holds a raw credential, CSRF value, password, reset secret, or verification secret.
- Every unsafe cookie-authenticated request requires exact configured `Origin`, a constant-time `X-CSRF-Token`/`estateflow_csrf`/server-record match, and valid access from that family. Credential-establishing/recovery mutations require exact Origin even without an access cookie.
- No credentialed CORS is enabled. The implementation must not trust `Forwarded`, `X-Forwarded-Origin`, or `X-Forwarded-For` to satisfy origin or client-source checks.
- Existing `requestLoggingMiddleware` emits method/path/status only. New code must preserve that posture and never add request bodies, cookie headers, secrets, email addresses, or raw IPs to logs/audit metadata.

### 1. Migration and persistence

| Proposed path | Symbols / change |
|---|---|
| `apps/api/prisma/schema.prisma` | Add `User`, `Credential`, `SessionFamily`, `AccessSession`, `RefreshSession`, `PasswordReset`, `EmailVerification`, `AuthAttempt`, `AuthRateLimitEvent`, and `SecurityAuditEvent` models plus relations, enums, unique constraints, and lookup indexes described below. |
| `apps/api/prisma/migrations/<timestamp>_ef120_auth/migration.sql` | Generated Prisma migration, reviewed before application. It creates the models/indexes only; no seed, backfill, account import, or destructive change. |
| `apps/api/src/features/auth/infrastructure/prisma-auth.repository.ts` | `PrismaAuthRepository`: transactional persistence implementation, including conditional refresh consumption and family revocation. |
| `apps/api/src/features/auth/infrastructure/prisma-auth.repository.test.ts` or `apps/api/test/auth.repository.integration.mjs` | Isolated Postgres tests for constraints, atomic rotation, expiry lookup, and revocation. Keep the test-table allowlist explicit if the existing cleanup helper is used. |

**Data model.** Use UUID primary keys generated by existing `pgcrypto` `gen_random_uuid()`, `timestamptz` timestamps, and UTC application values.

- `User`: `id`, canonical normalized account identifier (unique; email for this browser registration flow), `createdAt`, and `verifiedAt` nullable. It does not contain roles or organization data (EF-121).
- `Credential`: one-to-one with `User`; `passwordHash`, `passwordChangedAt`, `createdAt`, `updatedAt`. `passwordHash` is an Argon2id envelope only, never a password or a reversible derivative.
- `SessionFamily`: `id`, `userId`, `createdAt`, `revokedAt?`, and categorized `revokedReason?`. Index active families by user. A family is the revocation unit.
- `AccessSession`: opaque record `id`, `familyId`, `tokenHash` (unique), `csrfHash`, `issuedAt`, `expiresAt`, `revokedAt?`. Index active lookup by token hash/expiry and family. The raw access cookie is `id.secret`; only the identifier and keyed hash of `secret` are persisted.
- `RefreshSession`: opaque record `id`, `familyId`, `tokenHash` (unique), `csrfHash`, `issuedAt`, `lastUsedAt`, `absoluteExpiresAt`, `idleExpiresAt`, `consumedAt?`, `revokedAt?`, and `replacedById?`. Index lookup by identifier and active/expiry fields. The raw refresh cookie is `id.secret`; only the identifier and keyed hash of `secret` are persisted.
- `PasswordReset` and `EmailVerification`: `id`, `userId`, unique `secretHash`, `createdAt`, `expiresAt`, `consumedAt?`. Secrets are random 256-bit values, keyed-hashed, one-use, and expire in at most 15 minutes. No secret is stored in a URL or response.
- `AuthAttempt`: timestamped login outcome with only `accountKeyHash`, `clientSourceKeyHash`, and reason category. It supports exact rolling-15-minute failure count / cleanup; no raw account identifier or IP is persisted.
- `AuthRateLimitEvent`: endpoint kind, dimension (`ACCOUNT` or `CLIENT_SOURCE`), opaque keyed hash, timestamp, and outcome. Index `(endpoint, dimension, keyHash, createdAt)`. This permits independently configured rolling limits without a raw account/IP column.
- `SecurityAuditEvent`: opaque subject identifier when known, outcome, reason category, request correlation ID, and timestamp only. It must have no email, phone, location, raw IP, raw credential, session/token/CSRF/reset/verification value, or password-derived value.

A hash is `HMAC-SHA-256` under a required server-side auth hash key, encoded deterministically for indexed lookup. This is one-way for the high-entropy secrets and prevents simple dictionary lookup of normalized account/client-source values. The key is configuration, never persisted or logged.

**Atomic refresh/replay algorithm.** In one Prisma `Serializable` transaction, lookup the presented refresh `id`, verify the keyed hash with `timingSafeEqual`, and atomically conditional-update it from unconsumed/unrevoked/unexpired to `consumedAt`. In the same transaction create a new refresh record, a new 15-minute access record, and their new CSRF hash; revoke an access record tied to the consumed refresh if such a relation is retained. The new refresh retains the original `absoluteExpiresAt`; `idleExpiresAt` becomes `min(now + 24h, absoluteExpiresAt)`. A conditional-update count other than one means missing/expired/revoked/replayed: if it was consumed, revoke the whole family in that transaction, then return the generic refresh `401` and clear cookies. Retry only Prisma serialization conflicts with a bounded, tested retry; never retry a completed credential presentation as a new login.

| `apps/api/src/features/auth/infrastructure/node-crypto-password-hasher.ts` | Node 24 `node:crypto` asynchronous `argon2` adapter using `Argon2id`, 19,456 KiB memory, 2 passes, parallelism 1, a unique CSPRNG salt, and a 32-byte tag. Store an explicit versioned envelope containing parameters/salt/tag so successful login can rehash after an approved policy increase. |
| `apps/api/src/features/auth/infrastructure/node-crypto-credential-issuer.ts` | `randomBytes(32)`, HMAC-SHA-256 hashing, base64url codec, and constant-time equality with length guard. |

No authentication dependency is required for password hashing: Node 24.14.1 exposes `node:crypto` `argon2`/`argon2Sync`, verified in this planning environment. Use the async API only. Do not introduce JWT, Passport, bearer authentication, `cookie-parser`, generic CSRF middleware, a rate-limit package, or a provider SDK. A tiny local strict parser/serializer may be used only for the three base64url cookie values; it must reject duplicate/malformed auth-cookie names rather than accepting ambiguous input.

Login failures lock an account key for 15 minutes after ten failed attempts in the preceding rolling 15 minutes. Both account and client-source attempts are checked under a transaction/advisory lock keyed by opaque HMAC so concurrent requests cannot bypass the count. Registration, login, recovery, reset, and refresh each have distinct configured account and client-source limits. Client source derives only from the direct socket address, then is immediately HMACed; untrusted forwarding headers are ignored. Unknown account, bad password, temporary lockout, and recovery requests remain externally indistinguishable as required by ADR-007.

`EmailVerification` is created and delivered through the internal port on registration. Its public verification endpoint, external mail provider, retries, device binding/fingerprinting, mobile/bearer clients, roles, and organization membership are deliberately outside EF-120 unless a future approved packet supplies their contracts. EF-120 must not claim that a provider delivered an email.

### 4. HTTP, cookie, Origin, and CSRF boundary

| Proposed path | Symbols / change |
|---|---|
| `apps/api/src/features/auth/http/auth.controller.ts` | `AuthController` endpoints: `register`, `login`, `refresh`, `logout`, `session`, `requestPasswordRecovery`, `resetPassword`. Controllers parse/invoke/map only. |
| `apps/api/src/features/auth/http/auth.dto.ts` | Whitelisted DTOs for registration/login/recovery/reset and minimal session response; no token-bearing response type. |
| `apps/api/src/features/auth/http/auth-cookie.service.ts` | `setSessionCookies`, `clearSessionCookies`, exact names/options/max-ages, no domain attribute. |
| `apps/api/src/features/auth/http/origin.guard.ts` | `RequireCanonicalOriginGuard`, exact raw `Origin` equality for every POST route named above; reject absent/different origin and untrusted forwarded-origin headers with `403`. |
| `apps/api/src/features/auth/http/browser-session.guard.ts` | `BrowserSessionGuard`, access-cookie parse/validation and request principal attachment; missing/expired/revoked access is `401`. It ignores bearer credentials. |
| `apps/api/src/features/auth/http/csrf.guard.ts` | `CsrfGuard`, only after session validation: unsafe method check, header/cookie/server hash comparison in constant time, and `403` before handler execution. |
| `apps/api/src/features/auth/http/auth-request.ts` | Narrow typed request augmentation for authenticated principal/session family; do not use global `any`. |
| `apps/api/src/common/http/api-error.ts` | Only if needed to map typed auth failures to the existing `{ error: { code, message, requestId } }` envelope without exposing discriminating details. |

Endpoint contract:

| Endpoint | Success | Required boundary | Failure behavior |
|---|---|---|---|
| `POST /auth/register` | `202`, no secret/token | exact Origin + registration limits | validation `400`; duplicate/other account-sensitive outcomes are generic and do not expose a secret |
| `POST /auth/login` | `204` + all three cookies | exact Origin + login limits | unknown/bad/locked use the same generic authentication failure posture; no body token |
| `POST /auth/refresh` | `204` + rotated all three cookies | exact Origin + refresh limits + refresh cookie + CSRF header/cookie/record | invalid/missing/expired/revoked/replayed `401`, clear all cookies; replay also revokes family |
| `POST /auth/logout` | `204`, clear all three cookies | valid access + exact Origin + CSRF | missing/expired/revoked access `401`; CSRF/origin failure `403` with no revocation/rotation |
| `GET /auth/session` | `200` minimal principal | valid access cookie | `401`; never returns cookie/token values |
| `POST /auth/password-recovery` | `202` generic acceptance | exact Origin + recovery limits | always indistinguishable with respect to account existence; no delivery secret in body/log/URL |
| `POST /auth/password-reset` | `204` | exact Origin + reset limits + one-use secret supplied in POST body | generic validation failure for invalid/expired/consumed secret; revoke all user families on success |

Set cookies exactly: access `Max-Age=900`; refresh `Max-Age=604800` while server-side idle/absolute timestamps are authoritative; CSRF is rotated with refresh and its `Max-Age` must not outlive the fresh refresh's remaining absolute lifetime. Logout and invalid refresh send clearing `Set-Cookie` headers for all three names with the same Path/Secure/SameSite/no-Domain scope and `Max-Age=0`. Do not set an `Authorization` response header, return credentials in JSON, place secrets in a URL/query, or write them to storage/logs/audit events.

CSRF guard application is explicit rather than global until later mutation controllers are added. Every subsequent unsafe cookie-authenticated endpoint must compose `BrowserSessionGuard`, `RequireCanonicalOriginGuard`, and `CsrfGuard`; its implementation packet must add an API integration case for missing/stale/mismatched/cross-origin CSRF before it can ship.

## Acceptance criteria

EF-120 is acceptable only when all are demonstrated with fresh evidence:

1. Prisma migration applies forward to a blank guarded test database; schema has hash-only secrets and required indexes/constraints.
2. Node crypto uses Argon2id with memory >= 19,456 KiB, two passes, parallelism one, unique salt, parameter-retaining envelope, constant-time comparison, and rehash-on-approved-upgrade behavior.
3. Login and refresh set exactly three cookies with ADR-007 names, Secure/Lax/Path/no-Domain attributes, `HttpOnly` only on access/refresh, and 15-minute / 7-day max ages; no response body exposes a credential.
4. Refresh atomically creates a fresh access/refresh/CSRF set, preserves the original 7-day absolute expiry, renews idle only within it, and refresh replay revokes the entire family.
5. Valid access can read the minimal session principal; expired/revoked/missing access returns `401`; logout revokes its current family and clears every cookie.
6. Every listed unsafe route rejects absent/different Origin before side effects. Authenticated unsafe routes also reject missing, stale, mismatched, or invalid CSRF with `403`, no mutation, and no rotation.
7. Recovery response is generic regardless of account existence; reset/verification secrets are single-use, <=15 minutes, server-hashed, and never emitted to browser responses, URLs, logs, or audit data. Successful reset invalidates every user family.
8. Ten failures over the rolling 15-minute window apply a 15-minute temporary lockout; per-endpoint account/client-source limits are independently enforced while outward responses remain generic. Audit data contains only allowed opaque/minimal fields.
9. OpenAPI and generated client are regenerated and drift-free; client uses cookie credentials and injected CSRF for mutations, without bearer/token APIs.
10. All approved unit, integration, static, OpenAPI drift, and runtime smoke commands pass in the implementation packet. No provider, deployment, or real email delivery claim is made.

## Forbidden behavior and boundaries

- Do not use JWT/Bearer auth, mobile/API credentials, cross-origin credentialed CORS, wildcard origin, insecure development cookies, localStorage/sessionStorage for credentials, or an auth token response body.
- Do not trust forwarded-origin/IP headers; do not log/audit raw credentials, cookies, CSRF, reset/verification values, account addresses, phone, precise location, or raw IP.
- Do not create a public email-provider integration, device binding/fingerprinting, public verification endpoint, role/organization behavior, deployment, infrastructure change, provider account, production data, Git commit/push, or dependency change without its own authorized packet.
- Do not manually edit generated OpenAPI/client output or permit a later unsafe cookie-authenticated controller to omit any required guard/test.

## Migration forward/rollback note

Forward: generate and review a new additive Prisma migration, apply it only via the existing migration command against the guarded isolated test database, then verify schema and auth repository behavior. It creates no legacy data to backfill.

Rollback: do not run a destructive down migration against any shared environment. Before a future production-like application, take the required backup and use a forward corrective migration (for example, revoke/expire affected families and add corrective columns/indexes). In a disposable test database, the authorized test teardown may remove the database/container volume. This plan authorizes neither production application nor a rollback operation.
